- **Git workflow** — established the working pattern for this repo: commit the first/foundational changes directly to `main`, but branch (`chore/project-scaffold`) for the first substantive chunk of scaffolding work and merge it back via a reviewed step, in line with the branch/PR rule in requirements.md §4.
- **Marble controller prototype — implemented and running** — built and tested the first playable marble controller: `Marble.tscn` (RigidBody3D root, separate CollisionShape3D/SphereShape3D from MeshInstance3D/SphereMesh so the placeholder sphere can be swapped for a modeled/photogrammetry asset later without touching physics or code, PhysicsMaterial with bounce, Continuous CD enabled for tunnelling prevention), `MarbleController.cs` (direct-force movement via `Input.GetVector` + speed-capped `ApplyCentralForce`, per the direct-force control scheme requirements.md recommends as the primary target), and an Input Map (WASD + arrow keys). Wired up `Main.tscn` as a runnable test scene — floor (StaticBody3D), Camera3D, DirectionalLight3D and WorldEnvironment — so the controller is actually visible and testable in the editor, not just present in code. This satisfies the Week 1 milestone item "basic marble controller" and locks in the control scheme target in [project-plan-responsibilities.md §2](project-plan-responsibilities.md). Developed on `feature/marble-controller-prototype`, merged locally into `main`.
- **Camera framing for the test scene** — angled the `Camera3D` in `Main.tscn` down and back so the marble and floor are both in frame while tuning movement (first step toward the camera system owned under §1 of the project plan; the real follow/smoothing camera is still to do).
- **Migration to the official Classroom50 repo (20 Sep)** — moved the project history into the assessed `games-studio-2-cosc2349-assignment-3-marble-madness-group-5` repo by merging its Classroom50-generated `main` (`.classroom50.yaml` + stub README) into our history with `--allow-unrelated-histories`, keeping the full commit log intact for individual-contribution tracking rather than copying files in as one squashed commit. Kept our README over the generated stub and left `.classroom50.yaml` untouched so the autograde/registration config stays valid.
- **Tile convention spec and 2 m grid decision** — wrote [tile-convention.md](tile-convention.md), the shared spec the level/tile system is built against: tile origin at footprint centre so 90° rotation is safe, a walking surface fixed at y = 0, connection rules (flush edges, joins differ by at most one elevation step), naming and folder rules, CSG greybox rules, Blender export settings and the marble parameters tiles depend on. Each value is marked locked or tentative so teammates know what is safe to build against. Chose a 2 m × 2 m footprint (4 marble-widths, with a 1 m elevation step, so a one-tile ramp is a 2:1 slope of about 27°) over an initial 4 m proposal, in favour of assembling curves, forks and narrow paths from finer-grained pieces. Developed on `feature/tile-convention`.
- **CSG greybox tile kit and Level 1 prototype** — built the first modular tile pieces as reusable scenes following the convention: `TileFlat`, `TileRamp` (extruded `CSGPolygon3D` wedge), `TileHole` (slab with a subtracted cylinder, leaving a walkable ring so the gap is avoidable without a jump), and `TileArch` (thin wall with an arched cut-out), each on the 2 m grid with the walking surface at y = 0. Added shared colour-coded placeholder materials (grey, red, green, blue, yellow) so tile types are distinguishable at a glance and can be re-themed by swapping one resource. Assembled the tiles into `Level01.tscn` (multi-level layout with ramps up to a 4 m elevation) and replaced the test floor in `Main.tscn` with an instance of it, re-angling the camera to an isometric-style view. Kept CSG as a prototyping layer inside each tile scene so the meshes can later be swapped for baked/Blender assets without touching the level.

## Week 2 (24–30 Sep 2026)

- **Physics layer convention** — named the 3D physics layers in `project.godot` (`World`, `Marble`, `Hazards`, `Triggers`) and set the marble to layer `Marble`, colliding with `World` and `Hazards`. Documented the full per-object layer/mask table in [tile-convention.md §6](tile-convention.md), including for hazards and triggers Andrew hasn't built yet, so the convention is settled before more collision-bearing scenes exist.
- **Isometric camera follow rig** — built `CameraRig.cs`/`CameraRig.tscn`: a rig that tracks the marble's position with frame-rate-independent exponential smoothing (`1 - exp(-k·delta)`, not a fixed-alpha `Lerp`) while holding a fixed pitch/yaw/distance offset on its `Camera3D` child, so the view stays a consistent isometric angle rather than a generic third-person follow-cam. Exposed pitch, yaw, distance, follow speed and orthographic size as tunable exports. Diagnosed and fixed a case where `Distance` appeared to do nothing once the camera was switched to orthographic projection — under Orthogonal, translation along the view axis doesn't change apparent zoom, so added a separate `OrthographicSize` export driving `Camera3D.Size`, the property that actually controls zoom in that mode. Replaced the static test-scene `Camera3D` in `Main.tscn` with this rig. Satisfies the smoothed, isometric camera requirement (requirements.md §3.2). Developed on `feature/camera-follow`.
- **Checkpoint and respawn system** — added a `CheckpointManager` autoload (`scripts/Core/`) tracking the marble's current respawn point, a reusable `Checkpoint` trigger that updates it, and a `MarbleController.Die()` entry point that resets the marble's transform/velocity to the last checkpoint. `KillZone` (a large trigger below the level) and any future hazard both call `Die()` the same way — via `body.Call("Die")` duck-typing where only a `Node3D` reference is available — so hazard code Andrew writes later needs no dependency on `MarbleController`. Checkpoint/kill-zone triggers live on the `Triggers` physics layer, masked to `Marble` only. Added visible placeholder markers (translucent CSG box + material) so the trigger volumes aren't invisible while building. This overlaps with Andrew's owned checkpoint/respawn scope (project-plan-responsibilities.md §1) — built now to unblock testing, flagged for his review. Developed on `feature/checkpoint-respawn`.
- **Win state** — added a `GameStateManager` autoload signalling `LevelWon`/`LevelLost` (the latter unraised for now, reserved for the timer's lose condition so that system can plug in later without further changes here), a `Goal` trigger (same Triggers-layer pattern as `Checkpoint`/`KillZone`) that calls `Win()`, and a placeholder `WinMessage` UI that shows "YOU WIN" on the signal. `MarbleController` stops responding to input once the level ends. This is scaffolding across two other owners' scope (Andrew's win/lose, Jayden's UI, per project-plan-responsibilities.md §1) — built minimally so the game feel work isn't blocked, and flagged for their review. Developed on `feature/win-state`.
